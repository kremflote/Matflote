# MATFLOTE Master Document

Last verified: 2026-08-08

This is the current source of truth for MATFLOTE. It describes what the code does now, where important design decisions live, and which rough edges should be considered before larger changes.

Future ideas are listed only when they affect current architecture. They should not be treated as implemented behavior.

## Product Snapshot

MATFLOTE is a household meal planner, cookbook, grocery export tool, product scanner, price tracker, and nutrition planning aid.

Implemented pages:

- Planner: week/month meal planning, generation, prep helper, and grocery-list export.
- Cookbook: recipes, ingredients, images, tags, brands, nutrition, prices, conversion helper, recipe PDF export, and seed import/export.
- Scanner: EAN/barcode lookup through Kassalapp, nutrition enrichment through Matvaretabellen, and save-as-ingredient flow.
- Prices: ingredient price history by store.
- Nutrition: weekly approximate nutrition summary from planned meals.
- Settings: language, shopping-list provider settings, export rules, and system information.

Not implemented:

- Account system or cloud sync.
- Offline multi-device merge.
- AnyList export.
- Precise nutrition coaching or medical-grade nutrient advice.
- Separate "making food" versus "eating food" inventory/prep tracking.

Findings / follow-up:

- The app is now broader than the original dinner-planner concept. New features should be checked against the household/server-first scope before adding more planning abstractions.
- Nutrition is intentionally approximate. UI copy should keep setting that expectation.

## Architecture

Frontend:

- React + Vite + TypeScript.
- Tailwind utility classes, centralized through shared style files.
- The production frontend is static files served by nginx.
- In development, Vite normally runs on port 5173 and calls the backend at `http://localhost:5132`.
- In Docker, frontend API calls are same-origin because nginx proxies backend routes.

Backend:

- ASP.NET Core Web API on .NET 9.
- EF Core + SQLite.
- Migrations are applied on startup before request handling.
- `/health` is available for health checks.
- Backend also serves uploaded images from the configured image storage root.

Docker/server:

- `frontend` container: nginx serves built Vite files and proxies `/api`, `/images`, and `/health`.
- `backend` container: .NET API on internal port 8080.
- `matflote-data` volume stores SQLite data at `/data/dinnerplanner.db`.
- `matflote-images` volume stores uploaded and seeded image files at `/data/images`.

Findings / follow-up:

- The current Docker model is single-server sync: all devices point to the same MATFLOTE instance. This is compatible with a home Raspberry Pi setup.
- PostgreSQL is not required while one backend process owns the SQLite database. Revisit database choice only for account/cloud sync.

## Data Storage

Database entities currently include:

- Ingredients.
- Recipes.
- Recipe ingredients.
- Recipe components, where a recipe can be used as a measured ingredient in another recipe.
- Meal plans and planned meal items.
- Shared tag categories and tag definitions.
- Ingredient and recipe tag assignments.
- Brands.
- Stores.
- Ingredient price points.
- Nutrition facts per 100 g/ml.
- Nutrition reference profiles, values, and household nutrition preferences.
- Nutrition reference import runs.
- App settings.
- Grocery export rules.
- Conversion helper rules.
- Seed/import metadata.
- Uploaded image metadata.

Local storage currently includes:

- Theme mode.
- Language.
- Last open page.
- Cookbook view mode.
- Planner view mode.
- Separate planner week and month anchor dates.
- Planner generation people-eating value.
- Collapsed planner day sections on mobile/tablet.

Local storage intentionally does not store server data such as recipes, ingredients, prices, tags, or integration secrets.

Findings / follow-up:

- The draft storage list mentioned search/filter draft persistence. That is not implemented and was intentionally deferred.
- Nutrition `peopleEating` used to be per-device local storage. It is now stored as the household backend app setting `Nutrition:PeopleEating`.
- Uploaded image files are stored on disk, while metadata is stored in SQLite. Plain seed JSON contains image URLs; the export package endpoint includes image files.

## Backend Model Notes

Ingredient:

- Max name length is 40.
- Optional brand, description, image, price, tags, and nutrition data.
- Nutrition source can be `None`, `Manual`, `Kassalapp`, or `Matvaretabellen`.
- Color still exists for backward compatibility/fallback display, but current UI relies more on images and themed surfaces.

Recipe:

- Max name length is 30.
- Has a default `portions` value.
- Has normal ingredients and measured recipe components.
- Components use the same measurable units as ingredients.
- Tags are optional in the UI; the API receives a tag collection that may be empty.

Measurement units:

- `Gram`
- `Kilogram`
- `Milliliter`
- `Liter`

Preparation values:

- `None`, `Quartered`, `Wedged`, `Chopped`, `RoughlyChopped`, `FinelyChopped`, `Diced`, `Cubed`, `Julienned`, `Batons`, `Sliced`, `Minced`, `Grated`, `Shredded`, `Crushed`.

Meal planning:

- Meal slots currently exist as `Breakfast`, `Lunch`, `Dinner`, `Snack1`, and `Snack2`.
- Planned items may point to either a recipe or an ingredient.
- Recipe planned items store portions.
- Ingredient planned items store amount and unit.
- Planner week and month views keep separate anchor dates so switching view modes does not move the user's remembered week.

Findings / follow-up:

- `MealRecipeRole` still contains `Main`, `Sauce`, `Side`, and `Extra`. This is now mostly a display/export role, not a recipe-type system.
- Some historical migrations still contain old cuisine, dish type, and legacy vitamin concepts. That is normal migration history, but new code should not reintroduce those abstractions.
- `NutritionFacts` still has `VitaminKMicrograms` and `CholineMilligrams` for old local data compatibility. The Nutrition page does not surface them because current source coverage is not reliable enough.

## Tags

MATFLOTE now uses one shared tag pool for ingredients and recipes.

Current behavior:

- Tags live under tag categories.
- Categories and tags have sort order.
- The Manage Tags window supports create, edit, remove, move up/down, and category collapse.
- Deleting a category cascades its tags.
- Tags are used for filtering in browsers and for grocery export rules.
- Tags are no longer automatically assigned from scanner results.

Seeded starting categories:

- Produce.
- Protein.
- Pantry.

Findings / follow-up:

- The UI should continue avoiding hardcoded tag assumptions except where using a documented default, such as grocery export excluding `Spice`.

## Recipe Components

Old "sides attached to recipes" has been replaced with a simpler model: recipes can contain other recipes as measured components.

Example:

- A tomato sauce recipe can be added to spaghetti as `500 g`.
- Its underlying ingredients are shown under the parent recipe's ingredient section.
- Grocery lists and nutrition summaries should recursively account for component ingredients based on the selected amount.

Design rule:

- Treat a recipe component like a measured ingredient, not like a side serving.
- Avoid density/yield conversion beyond the selected unit. The app assumes simple pre-cook measurement.

Findings / follow-up:

- This model is intentionally simpler than a true cooked-yield model. It fits the current "planning and shopping approximation" goal.
- If we later need post-cook yield, batch inventory, or leftovers, that should be a separate design pass.

## Planner

Current behavior:

- Week and month views.
- Week view is the primary meal planning surface.
- Mobile/tablet uses persistent top header and bottom navigation.
- On mobile/tablet, planner tools are behind a floating icon button.
- Meal picker can select multiple recipes and ingredients in one flow.
- Recipe selection asks for portions.
- Ingredient selection asks for amount and unit.
- Selected items are shown as compact thumbnails in the picker footer and can be removed from there.
- Generate asks how many people are eating this week. That value defaults to 2 and is stored per device.
- Generator only fills empty slots and does not select ingredient-only entries.
- Generator uses system tags for breakfast, lunch, dinner, bread, topping/`Pålegg`, fish, and chicken rules.
- Breakfast slots use Breakfast-tagged recipes. Lunch slots use Lunch-tagged recipes. Dinner slots use Dinner-tagged recipes.
- Dinner recipe selection avoids selecting the same dinner recipe more than once in a generated range, while allowing leftover placements from that selected recipe.
- Breakfast and lunch recipes may repeat across the week.
- A generated meal slot uses the people-eating value as its planned portions. If the selected recipe's default portions can cover more compatible future slots, the leftover portions are placed into those future empty slots. Leftovers that cannot feed the selected number of people are discarded.
- Dinner leftovers may be placed into future lunch or dinner slots. Breakfast/lunch leftovers stay in matching slots.
- Bread breakfasts can add a `Pålegg` ingredient side, with a maximum of two distinct `Pålegg` ingredients per week.
- Dinner generation tries to include at least one fish dinner and two chicken dinners when matching recipes exist, then favors protein variation.
- Clear week/month uses the styled confirmation dialog.
- Prep helper gives a quick weekly prep list.
- Grocery export opens a preview dialog before sending to Vikunja.

Findings / follow-up:

- The generator depends on system tags being present and assigned meaningfully. Recipes without the relevant meal tags will not be generated for those slots.
- The people-eating value used by the generator is per-device local storage, while the Nutrition page's people-eating setting is a household backend setting. They currently serve different workflows and are intentionally separate.
- Month view is useful for overview but remains less feature-rich than week view.

## Cookbook

Current behavior:

- Recipes/ingredients toggle.
- Search.
- Ingredient filter popover.
- Category/tag filter modal on portable widths.
- Floating add button on mobile/tablet.
- Shared recipe and ingredient browser components.
- Create/edit/detail flows use shared modal framing.
- Recipes and ingredients support image upload/crop controls.
- Ingredient editor supports brands, tags, nutrition, prices, and images.
- Recipe editor supports portions, tags, details, image, instructions/description, ingredients, and recipe components.
- Conversion helper is available while editing recipes.
- Recipe detail can export a compact A4 PDF from the backend. The PDF includes MATFLOTE branding, the GitHub repository URL, recipe image, description, ingredients, instructions, and a secondary approximate dietary summary.

Findings / follow-up:

- `recipeBrowserStyles.ts` is large and carries browser, form, modal, tag, image, and picker styling. Future styling cleanup should split this by responsibility while preserving centralized tokens.
- Most modals use the shared `Modal` component, but modal-specific panel class names still live in several style namespaces. Keep new modal work on the shared frame pattern.

## Scanner

Current behavior:

- Desktop shows manual EAN entry first.
- Mobile/tablet emphasizes camera scanning.
- Camera access requires a secure origin in normal phone browsers, so production should use HTTPS.
- Barcode lookup goes through the backend; the frontend never receives the Kassalapp API key.
- Kassalapp provides product identity, brand, image, price/store, and nutrition when available.
- Matvaretabellen is used to fill missing nutrition fields when a match is found.
- Users can manually choose a Matvaretabellen match or search Matvaretabellen from the nutrition editor.
- Saving uses the normal ingredient API.

Findings / follow-up:

- Scanner matching is useful but not guaranteed. The editor must always let the user correct or blank values before saving.

## Prices

Current behavior:

- Stores are database lookups.
- Default stores are seeded: Rema 1000, Coop Mega, Coop Prix, Coop Obs, Coop Extra, Meny, Kiwi, Bunnpris, Europris.
- Ingredient info and edit/create flows can add price points with date, store, price, and optional note.
- Prices page displays tracked price data.

Findings / follow-up:

- Price tracking is local household data. There is no implemented feature for sending personal price points back to Kassalapp.
- Future offer tracking would need a separate importer/comparison service.

## Nutrition

Current behavior:

- Weekly nutrition is calculated from the selected date range's planned meals.
- Recipe portions and ingredient amounts are included in calculations.
- "People eating" divides displayed per-person totals and daily calories.
- Daily calories are shown without goal judgement.
- Reference-value cards are shown only for nutrients with reference data.
- Missing nutrition warnings list ingredients with incomplete/absent nutrition data.
- Profile preference is stored as a backend app setting.
- Reference values can be imported from Helsedirektoratet HAPI and are stored locally.
- Kassalapp nutrition is prioritized for scanned products; Matvaretabellen fills only missing fields.

Displayed nutrients are aligned with what the current sources can realistically provide:

- Carbohydrates.
- Protein.
- Fiber.
- Saturated fat.
- Monounsaturated fat.
- Polyunsaturated fat.
- Omega-3.
- Vitamin A.
- Vitamin B9.
- Vitamin B12.
- Vitamin C.
- Vitamin D.
- Vitamin E.

Tracked but not judged as weekly targets:

- Calories by day.
- Total fat in ingredient/recipe detail.
- Salt and other fields in ingredient detail where available.

Findings / follow-up:

- Nutrition source coverage is uneven. Weekly numbers should always be described as planning estimates.
- Minerals are intentionally not included.
- Calories are not compared to a target because energy needs depend on personal factors not modeled in MATFLOTE.

## Grocery Export

Current behavior:

- Grocery list preview is built from the current planner range.
- User can deselect items before export.
- Export rules can default-disable ingredients with selected tags. `Spice` is the default if no setting exists.
- Vikunja is the first provider.
- Export mode supports one task with checklist or separate tasks.
- Provider settings can be configured on the Settings page.

Findings / follow-up:

- The exporter is provider-shaped, so another todo provider can be added later without rewriting grocery-list generation.
- Integration secrets must stay in user-secrets, `.env`, or backend app settings. They must not be committed.

## Seed Catalog And Images

Current behavior:

- `backend/SeedData/catalog.json` is imported on backend startup after migrations.
- Import is additive and avoids overwriting existing matching data.
- Seed export endpoint can export tags, tag categories, conversion rules, brands, ingredients, recipes, and recipe components.
- Export package endpoint includes image files as well as JSON.
- Bundled seed images are copied to configured image storage if missing.

Findings / follow-up:

- Plain JSON export does not include binary image files. Use the export package endpoint before risky deploys or migrations on the Pi.
- The committed seed catalog is currently empty, so production instances mostly contain user-created data unless a curated catalog is added.

## Settings And Integrations

Settings currently covers:

- Language selection.
- Current shopping-list provider.
- Vikunja URL/project/token.
- Export task mode.
- Kassalapp base URL/API key.
- Helsedirektoratet base URL/subscription key.
- Grocery export tag rules.
- System information such as environment, database provider, and image storage path.

Configuration sources:

- Backend appsettings files for non-secret defaults.
- User-secrets for local secret development.
- `.env` or server environment for Docker secrets.
- Database app settings for values edited in the Settings page.

Findings / follow-up:

- Secrets are write-only in the Settings page. The UI shows whether a key/token is configured, but never displays the saved value.

## Design System

Core design direction:

- Clean, friendly, readable, structured.
- Reuse centralized values rather than one-off measurements.
- Prefer compact operational UI over marketing-page layout.
- Use actual UI surfaces, not decorative hero sections.

Typography:

- Main interface font is Nunito.
- Logo uses Ubuntu bold 700.
- `typographyClasses` in `frontend/src/styles/appStyles.ts` is the code source for the current typography classes.

Spacing:

- Use the 8 px rhythm wherever possible.
- Allowed base values: 4, 8, 16, 24, 32, 48, 64, 96.
- Tailwind classes may express these as `gap-1`, `gap-2`, `gap-3`, `gap-4`, `gap-6`, `gap-8`, `p-4`, etc.
- One-off pixel values should be reserved for solving a precise responsive/layout issue and should be centralized if reused.

Radius:

- The active app uses `rounded-md` as the dominant shape for controls, cards, modals, and thumbnails.
- The theme switch is an intentional exception and remains rounded/pill-like because that is the expected control shape.

Colors and surfaces:

- Theme colors live in `siteColorClasses`, `surfaceClasses`, and `colorPalette`.
- Shadows live in `shadowClasses`.
- Modals should use `surfaceClasses.modal(theme)` and shared modal shell patterns.
- Selected thumbnail borders use the centralized selected border color.

Responsive rules:

- Desktop uses normal top navigation and wide page content.
- Mobile/tablet breakpoint is currently `max-[1100px]`.
- Mobile/tablet uses fixed header, bottom navigation, floating action buttons, and more modal-driven filter/tool flows.
- `pageStyles.shell`, `sizeClasses.portableFixedHeaderOffset`, and `sizeClasses.portableBottomNavOffset` handle the fixed header/nav spacing.

Findings / follow-up:

- The original draft said cards use 24 px radius, but the app has intentionally moved to smaller `rounded-md` shapes. Keep the implemented shape language unless a future redesign says otherwise.
- `appStyles.ts` has become the central design registry and is large. It is still preferable to scattered one-off classes, but future refactors should split by domain without duplicating tokens.

## Language

Current behavior:

- English and Norwegian are supported.
- Language is stored in local storage.
- UI copy should go through `frontend/src/i18n`.
- Domain terms should stay consistent:
  - Cookbook: "Cookbook" / "Kokeboka".
  - Planner: "Planner" / "Planlegger".
  - Scanner: "Scanner" / "Skanner".
  - Tags stays "Tags" in Norwegian where intentionally chosen.

Findings / follow-up:

- New UI strings are easy to miss because many features have been added quickly. Treat missing translation coverage as a normal check before finishing a feature.

## Deferred Ideas

Ideas that are deliberately not implemented yet:

- Ingredient substitution/similarity system.
- Offer/price comparison against external store data.
- Export recipe as PDF.
- True account-based sync.
- Leftover/rest-food inventory model.
- More advanced conversion helper that suggests units from selected ingredients.

Any of these should get a fresh plan before implementation.
